1. The supplied assessment is directionally right—but needs calibration

I agree with its central recommendation: prioritize Altitude and Depth—pursuing a bounded goal, using raw evidence and an outside judge—before expanding feature count or general multi-agent capacity. The original Felix Rieseberg article was verified as published on 13 October 2026 and does name Speed, Altitude, Depth and Range.

However, this is largely a convergence strategy already present in the project, not a reason to redesign it. docs/ROADMAP.md:15–28 already says “Do not build more system,” then specifies one natural Problem, 5–10 cases, measured economics and simplification.

What the assessment gets right

  • UI state must not impersonate runtime execution, controller acceptance or user outcome.
  • Tests, operational proof and a user result are different evidence levels.
  • Continuation needs budgets, STOP, authority and replay-safe recovery.
  • Knowledge should reuse causal evidence, not become a competing authority.

What I would correct

  • Work Hub is partly preparatory; the backend is not merely a mock-up.
  • “Not verified today” does not mean “never implemented or exercised.”
  • Background continuation modules and Goal-episode parents already exist.
  • Outcome evidence is incomplete, not literally absent from all history.
Do not collapse all completion into one flag. A technical change can be accepted while rollout or user outcome is pending. Group work around the Problem/Outcome, but retain separate source, proof, technical acceptance, activation, release and outcome dimensions. Otherwise “outcome-driven” becomes another source of misleading status.

4. The gaps worth fixing first

  1. Source → installed runtime provenance. Local HEAD, dirty worktree, remote main and the running installation differ. Preserve concurrent work; identify the intended candidate and its exact component fingerprints. Do not “fix” this with a reset or an unapproved restart.
  2. Truthful UI semantics. Rename local queue state and feedback acknowledgement so they cannot be mistaken for runtime receipt/ACK. A preparation feature may remain preparation-only; it simply must say so.
  3. Patch approval is insufficiently scoped. work-hub-store.js:391–404 keys approvals by relative path only. An in-memory reproduction confirms the lack of workspace identity. Same path and diff across projects can reuse a visual approval. It is advisory—not an observed runtime authorization exploit. Immediately scope review state; connect any future actual authorization to the existing exact patch/grant path. A stronger hash alone would not solve missing authority.
  4. Job identity is not output durability. artifact_refs.py:96–104 explicitly declares command output process_runtime and restart_safe=False. Either persist the evidence needed for review through the existing artifact path, or clearly declare it unavailable after restart. Do not advertise durable logs based on durable Job IDs.
  5. Continuation source is ahead of operational proof. Existing Goal parents reuse RUN-like maximums of 900 seconds, 12 decision turns and 3 patch attempts. That is not the plan’s full 60-minute / four-episode / 32-turn / eight-patch proposal and reservation accounting. Begin with the smaller supported contract; implement only the demonstrated missing budget semantics.
  6. Host execution has a real safety boundary. Current source defaults Windows to local host-user execution. Workspace checks are not an OS sandbox. Confirm loaded mode, bounded operations and protected paths before unattended writes. Also test cross-workspace recipe cwd admission and manual editing during an active writer lease; this audit does not claim an exploit there.

The product risk is disconnected promises, not simply missing features. A renderer can show completion, a Job can exit, a technical review can pass, and the user’s problem can remain unresolved. Bind those claims through the existing canonical records instead of adding another status database.

6. The first practical acceptance pilot

Recommended Goal: fix one genuine, reproducible low-impact Codex-web defect through Work Hub and the existing execution channel; deliver the exact diff, a behavior-specific proof, and a reviewable result without needless relay after the authorized start.

The approval cross-project case found here is a candidate, but the operator must confirm it matters in real use. Do not manufacture synthetic work and label it a natural outcome. Preserve concurrent edits and choose a non-overlapping defect or controlled candidate if needed.

  1. Reproduce the actual failure; define the independent behavior oracle, allowed paths and explicit budget before mutation.
  2. Read back exact machine/workspace, Problem revision, controller and source identity; submit once and capture its durable handle.
  3. Observe a scoped fix and proof on those bytes. Keep test code and the user-visible behavior check distinct.
  4. End the initiating response. Verify a necessary next action continues under the same grant, without a manual relay.
  5. In separate controlled fault checks, test STOP, duplicate start, lost response, stale source and restart with a pending effect. Do not count those checks as natural business outcomes.
  6. Finish at the correct review boundary. Obtain the actual user outcome receipt or retain WAITING_REVIEW/WAITING_USER_OUTCOME; reopen when the user’s original problem remains.
Success is zero unnecessary relay, not zero human decisions. New permissions, changed scope, increased budget, technical review and user outcome confirmation remain legitimate decisions. An Ubuntu gateway being online cannot execute Windows-only work while the required Windows executor is offline.

Full BG01–BG14 remain the target contract. A smaller single-episode pilot is a staged milestone, not a declaration that the full background-Goal plan is complete.

Verified Outcome RateEligible exact Problem revisions with valid outcome confirmation / all eligible revisions started in a predefined cohort window. Report pending, blocked and missing follow-up separately; do not silently omit them.

A 5–10-case cohort is a calibration and feasibility set. Match task class, source, environment, model/route and oracle where possible. Larger or prospective controlled evidence is needed before asserting causal improvement or promoting automatic routing.

For reusable knowledge, capture symptom → trigger conditions → root cause/hypothesis confidence → rejected explanations → fix → independent proof → follow-up → early warning. Retrieve it as a hypothesis and revalidate current conditions; never derive write or acceptance authority from an old case.
